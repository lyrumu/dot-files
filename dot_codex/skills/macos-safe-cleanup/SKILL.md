# macOS 安全盘点与确认式清理

这是 lyrumu 的个人工作流。每次从当前磁盘状态重新发现候选，不把历史清单当删除白名单。默认中文沟通。

## 不变的约定

- 新会话调用或“再查一次”只授权盘点；先列清单，用户选定当次编号/精确路径后才清理。历史批准不跨批次延续。“清理一下”未指定目标时，先盘点而非自动执行。
- 默认排除 `/Users/lyrumu/.cache/opencode`，包括扫描生成的任何父目录清理方案；不要顺带清理项目内 `.opencode` 依赖。只有用户明确改变此排除项才重新讨论。
- 用户数据与缓存名称不是同义词。`Caches` 里可能有录屏；`CacheStorage` 可能有离线内容；剪辑软件缓存可能含 TTS、草稿和生成结果。只看路径或大小不能证明可删。
- 不安装清理软件/依赖，不改 shell 配置，不添加定时任务、服务、触发器或全局包。终端每组命令加中文 `#` 说明。正常盘点完全离线；确需联网时先在同一 zsh 中验证用户的 `proxyon` 有效，不改持久代理设置。
- 本技能不授予系统权限。不隐藏拒绝后换命令达到同一受阻写入；按当前工具规则申请所需权限/升级执行，仍被拒绝则停止该项并报告。不要关闭 SIP、更改目录所有权或扩大权限。

## 1. 每次重新发现

先读 [盘点范围与鉴别方法](references/discovery.md)。它是覆盖范围，不是固定候选列表；初始排名后必须展开之前没出现过的新大目录。

读取 [本机历史](references/host-history.md) 仅用于解释排除项、对比旧批次和识别坑，不能把旧版本/尺寸当当前事实。

1. 记录日期、实际用户目录、macOS 数据卷 `df -k`。不使用只读系统卷 `/` 的 Used 代替整个数据卷。
2. 分别盘点用户顶层（含隐藏目录）、Library、系统常见数据目录、下载/录屏、项目生成产物。按大小向下展开；不跟随符号链接跨越原范围，不扫描挂载的网络/外置盘，除非用户点名。
3. 动态搜索缓存/更新目录，并检查较大文件类型、名称、时间、所属应用、是否当前版本。无需读取私人文件正文、聊天内容、凭证或浏览历史。
4. 权限错误、工具失败和截断都列为覆盖限制。不能把 `2>/dev/null` 后的无输出当“空目录/未占用/不存在”。不要声称全系统每个文件都已检查。
5. APFS 稀疏文件和克隆注意区分逻辑长度与 `du` 分配空间，后者也不一定等于真正可释放的独占空间。不要加总父子目录重复统计。

## 2. 给出可批准清单

每批独立编号并标注日期。每个可批准项目给出：绝对路径、实测 KiB/MiB/GiB、用途/可删依据、清理后影响、是否必须退出应用、保护/不确定项。父目录混合重要数据时只列已确认子目录。

分为：

- **可重建缓存候选**：HTTP/代码/安装包缓存等；清后可能重下、离线不可用、下次构建更慢。仍须确认。
- **需要判断**：个人下载/录屏、离线网页、项目依赖、旧发行版、剪辑资源、更新回滚副本等。
- **保留/待诊断**：应用数据库、聊天/媒体/草稿、运行时、模型、系统管理缓存、不明临时文件、权限不可读部分。

不要把 npm/npx/uv 等“可重下”说成“没用”。不要批量清空 `Library/Caches`、`Application Support`、`Containers`、`.cache`、`.codex`、`/private/var/folders`。

把完整候选报告写入当前任务 `outputs/`；表中可批准目标必须是展开后的精确路径，不能拿 `*` 当最终删除目标。结束扫描后等待用户选择；本步骤不修改候选文件。

## 3. 用户批准后的预检

仅处理当前批准清单。跨日或大小/内容/版本变化时重验；出现新个人文件、目标身份改变或范围不明则暂停该项询问。

- 检查路径、真实路径、文件类型、所有者/ACL/flags、大小、mtime 和符号链接。拒绝宽泛根目录、父目录覆盖排除项、重叠目标、解析后越界目标。
- 浏览器/剪辑软件/IDE等写入者应先正常退出；不要强杀进程或丢弃未保存内容。用获准的进程查询与 `lsof` 辅助，检查退出码/错误；无输出不等于已证明没有写入者。无法确认时让用户关闭相关应用，跳过被占用项。
- 更新副本对比正式 `/Applications/.../Contents/Info.plist` 与副本版本、更新状态；同版本不自动证明所有安装支持目录都可删。新于正式版本的是待更新资源，不当旧垃圾处理。
- 项目产物先读 `git status`、相关构建/依赖配置和目录结构，确认无需保留的交付物或用户改动。不能为释放空间改源码或锁文件。

**先留审计记录**：在当前任务 `outputs/` 保存本批顶层目标、批准范围/时间、清理前大小以及逐文件的原始绝对路径清单（建议含类型、逻辑大小、mtime）。只记元数据，不复制文件内容。使用可安全表示空格/换行的格式，如 JSONL 或 NUL 分隔；遇读取失败必须披露。记录临时落点映射及每项目执行状态。不要等删完才发现没有准确清单。

## 4. 精确执行与权限

先说明最终是“可恢复移入废纸篓”还是“永久删除”。默认采用可恢复移动。永久删除前必须明确告知不可恢复，并取得对本批精确目标的永久删除授权；单纯“释放空间”不自动覆盖可恢复模式。已在当前批次取得明确永久授权时不重复索要同一确认。只处理本批目标，不能清空整个废纸篓。

- 原生 `/usr/bin/trash --verbose --stopOnError` 可作为可恢复方式。该工具曾错误退出仍返回 0；必须检查输出、原路径是否消失、实际废纸篓落点是否存在。不能猜测重名后的落点。
- 如果需要隔离目录，先获得真实写入权限，再用 `mktemp -d` 在任务 `work/` 创建唯一空目录，明确映射每个获批源路径。逐项移动且失败立即停止该项；核对成功移动的内容后，才按用户选择保留或永久移除。隔离不是绕过沙箱/安全拒绝的方法。
- 获权后用当前工具允许的删除方式处理精确目标。不把多个步骤无条件串起来；部分失败时分别报告 moved/deleted/failed/preserved，不误报全部成功。
- 不使用未解析变量、通配符或扫描输出直接拼成删除命令。不要为了清理而改环境、执行全局 prune、VACUUM、删除 SQLite WAL、卸载运行时或启动 Docker。

## 5. 核验与交付

核对原路径与暂存落点，保留清单中的相邻项目/正式应用和 OpenCode 排除项。运行状态未测就只说“版本文件仍在”，不说“应用功能正常”。若应用重建缓存，区分原内容已删除与新目录再生成。

记录 `df -k` 前后差值与原 `du` 总量，明确后台写入、APFS 克隆/稀疏/快照等使两者不同；移入同盘废纸篓/隔离目录不算释放空间。清理只启动了哪些诊断进程，就关闭哪些；不要终止用户原有服务。

最终给出：成功/跳过/失败精确路径、总计与实际空间变化、是否可恢复、仍保留项、完整审计报告链接。不要把过往成功操作当本次完成。
